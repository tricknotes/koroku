# koroku のアプリを軽くする

koroku は VPS 1 台に 3〜5 個のアプリを載せる。アプリごとのメモリは、koroku の「リソース」タブと各サービスのメモリ上限（既定 512m）で見えている。この Skill の仕事は、本番と同じ構成を手元で動かして測り、判断の小さいものから順に変えて、効いたものだけを残すこと。

## 進め方

### 1. 目標と測り方を決める

- 目標は「全サービスの `docker stats` の合計」で置く（koroku のリソースタブと同じ値）。「80% にする」なら、変更前の合計の 80%。
- 測るのは負荷をかけて落ち着いたあとの値。起動直後は小さく出すぎ、負荷の最中は一時的に大きい。
- 本番のアプリのリソースタブの値（とメモリの履歴）があれば、それも控える。手元の値と大きく違うなら、データ量や負荷の違いを先に疑う。

### 2. 本番の構成を手元で動かして、変更前を測る

1. 本番用のイメージを手元でビルドする（private なレジストリのイメージは pull できないことが多い）。
2. prepare-app Skill の `scripts/rehearse.sh --keep` で、koroku と同じ override を重ねて起動する。最後に Compose のプロジェクト名が出る。
   - テスト用の env ファイルには、必須の変数に仮の値を入れる（本物の秘密は使わない）。
   - DB が空だと、ページが軽すぎて差が出ない。seed やテスト用のデータを入れる（`docker compose exec`）。
3. [scripts/measure.sh](scripts/measure.sh) で測る。

```sh
<skill-dir>/scripts/measure.sh --project <name> --host <本番のホスト名> --path / --path /items --path /items/1
```

- 公開ページを 5〜10 種類選ぶ。重いページ（一覧、検索、フィード）を必ず入れる。
- 最初に出る各ページのステータスを見る。301/302/403 ばかりなら、測っているのはリダイレクトや拒否の速さになる。ホスト名の検査（Rails の `config.hosts`）や正規ホストへのリダイレクトがあるアプリには、`--host` に本番のホスト名を渡す。
- **同じ条件で 2 回以上**測る。同じイメージでも数 MiB〜十数 MiB ぶれる。マシンがほかの作業で混んでいるときは、変更前と変更後を交互に測って比べる。

### 3. 判断の小さいものから順に試す

[references/techniques.md](references/techniques.md) の順に、1 つずつ入れて測る。効かなかったものは戻す（設定が増えるだけで得がない）。

1. 設定だけで済むもの: スレッド数、アロケーターと GC の環境変数、サイドカーの Go の GC。
2. プロセスの数を減らすもの: 別プロセスのワーカー（ジョブ）や、定期ジョブのためだけのスケジューラーを Web サーバーの中で動かす。たいてい最も効く。スケジューラーの移し先（koroku の定期タスクを含む）は techniques.md の候補から利用者に選んでもらう。アクセスがない間の休止を使うアプリでは、アプリの中のスケジューラーは休止中に止まるので、koroku の定期タスクに移す。
3. 依存を減らすもの: 本番で使っていない gem・パッケージ、重いライブラリの軽い代替。
4. 速さと引き換えのもの: YJIT を止める、DB のキャッシュを小さくする。**入れる前に性能を測り、数字を利用者に見せて判断してもらう。**

次のような、設計の判断が要る変更は実装しない。プロダクトの設計と運用の両面からトレードオフ（得られる量、失うもの、運用で増える手間）を書いて止める。

- フレームワークや言語の置き換え（例: Sinatra を素の Rack に、Rails を別のものに）
- アーキテクチャの変更（例: cron のジョブを常駐プロセスにまとめる、サービスを分ける・まとめる方針の変更）
- 機能やサービスを削る変更

### 4. 確かめる

- ページがすべて 200 で返る（負荷の前後で）。
- ジョブを動かす構成を変えたなら、ジョブを 1 つ投入して、取り出されて実行されることをログで見る。止めるとき（`docker compose stop <service>`）に、ワーカーも行儀よく止まること。終了コードは変更前と比べる（Puma は変更前から 1 で終わることがある）。
- 速さに関わる変更（GC を強める、YJIT、スレッド数）は `measure.sh --bench` で、変更前と変更後の応答時間（p50・p95）とスループットを比べる。マシンが混んでいるなら交互に 3 回ずつ測って中央値で比べる。
- リポジトリのテストと lint を通す。
- 本番では測っていないことを明記する。デプロイしたら、koroku のリソースタブとメモリの履歴で確かめるよう利用者に頼む。

### 5. 報告する

- サービスごとの表（変更前・変更後、それぞれ複数回の値）と合計、変更前に対する割合。
- 1 つずつの変更と、その効き目（入れた順の累積でよい）。効かなかったので入れなかったもの。
- 速さと引き換えにしたものがあれば、その数字。
- メモリ上限を変えたなら、その値と理由（まとめたサービスの上限は上げ、全体の上限の合計は下がる、など）。
- 判断を利用者に残したもの（設計の変更、DB のキャッシュなど）と、その見込みの量。
- 確かめていないこと（本番の値、重いジョブの実行中、など）。

## 気をつけること

- **一度に 1 つずつ**変える。まとめて入れると、どれが効いたか分からず、効かないものが残る。
- アロケーターの設定だけでは効かないことがある。理由と組み合わせ方は techniques.md の「jemalloc」。
- 手元の負荷テストと本番の使われ方は違う。手元で 70% でも、本番のデータ量では変わる。目標にぎりぎりなら、余裕のある組み合わせを選ぶか、そう書く。
- 計測のスクリプトやログはリポジトリにコミットしない（`.git/info/exclude` に入れるか、リポジトリの外に置く）。
